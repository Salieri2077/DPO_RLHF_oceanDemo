# M2：零样本评估与 C0 示范数据（进行中）

对应 [SKILLRL_OCEAN_DESIGN.md](SKILLRL_OCEAN_DESIGN.md) 的 M2。Agent 起点为官方 Qwen3-1.7B Instruct（设计 7.1），这里记录它在新任务上未经任何适配的成绩、错误类型和实际预算用量，作为 C0 共同适配的诊断依据，不作为主比较基线。

## 设置

- 模型：`/data/anhuang/oceanheart_models/qwen3-1.7b`，无 adapter，非思考模式。
- 环境与评分：M1b 的 `OceanLabHarness` 与评分器；请求为 `oceanlab_dev_v1` 的 48 条。
- 采样：每条请求 1 条 greedy、8 条采样（T=1，与 RL 采样设置相同，种子按请求和样本固定）。
- 预算故意放宽，用于测量：单轮最多 1,024 新 token，上下文 16,384，最多 20 次调用、24 轮。
- 脚本：`scripts/run_oceanlab_eval.py`；结果：`artifacts/oceanlab/m2/zeroshot-instruct-20261010-1650-*`。
- 显存：Qwen3 的分组 KV 在 2080 Ti 上会让 SDPA 退回朴素算法，8K 提示即显存不足。评估脚本先展开 KV 头，16K 提示峰值为 5.8 GiB。

### 模板选择（greedy，规则事先固定）

| 模板 | 成功 | 以合规 `<final>` 结束 | 工具调用无错误 |
|---|---:|---:|---:|
| MiniMind 代理模板 | 0/48 | 12.5% | 21.3% |
| **Instruct 自带模板** | 0/48 | **35.4%** | **30.8%** |

两者首轮提示完全相同，差别只在历史轮次：MiniMind 模板在之前的助手轮里保留空的 `<think></think>`，自带模板会去掉，后者是模型训练时见过的格式。按规则选择自带模板，后续都用它。

## 结果

| | greedy | 采样（8×48） |
|---|---:|---:|
| 科学成功 S | 0/48 | 0/384 |
| 平均奖励 r | −0.054 | −0.047 |
| 出现协议违规的 episode | 54% | 47% |
| 可算任务答成“支持不足” | 7.3% | 15.5% |

- pass@8 = 0：48 条请求的 8 条采样全部失败。
- 43 组的 r 有变化，但都只来自协议罚项。按设计，这不算科学学习信号，所以零样本起点不能直接做 RL。
- 4 个任务族的成功率都是 0。

### 失败在哪一步（432 条轨迹）

| 阶段 | 轨迹数 |
|---|---:|
| 至少有一项要求的分析从未算出 | 203（47%） |
| 都算了，但参数不对 | 186（43%） |
| 所有分析都算出了参数正确的句柄，交付失败 | 43（10%） |

最后一类的交付失败原因：
- 30 条在算出正确句柄后继续读结果、重复调用，直到预算耗尽；
- 11 条在 `<final>` 里抄写数值而不是句柄；
- 1 条状态判断错误；
- 1 条句柄写错。

### 参数错误类型（各 episode 中最接近正确的句柄）

| 参数 | 次数（最接近的句柄） | 主要形式（按全部句柄计） |
|---|---:|---:|
| 分组 | 190 | 季段应合为一组却拆开或数目不对（143），单月或季段的日期边界不对（99），多个月份数目不对 |
| 区域 | 153 | 南纬、西经的正负号或上下限顺序错（108 个句柄），其他框选错误（139 个句柄） |
| 深度层 | 51 | “上层 X 米”误从 0.494 m 起，或把 X 当作起点 |
| 变量 | 7 | 用盐度代替势温等 |

区域错误示例：请求“西经180°—西经170°”，模型调用 `lon_min=-170, lon_max=-170`，工具报错后一再重试仍然错。

### 协议违规与一个环境缺陷

无法解析的动作共 1,561 轮：
- **884 轮是因为 `<plan>` 里出现了 `<`。** 模型把工具报错文字里的“-180 ≤ lon_min < lon_max ≤ 180”抄进了 plan，而协议规定 plan 里不能有尖括号。这类情况集中在 76 条 episode，这些 episode 随后反复重试同一个被拒的动作。**这是环境缺陷**：环境自己的报错文字诱发了协议违规，而且解析错误的提示没有说明 plan 里禁止尖括号。
- 451 轮是标签不完整，例如 `<final>{…}></final>` 多了一个 `>`。
- 其余是 JSON 不完整和未知工具。

其他工具错误：
- 632 次重复失败调用、376 次重复成功调用：模型反复做同一件事。
- 335 次经纬度范围不合法、95 次越过分区、45 次深度范围内没有标准层。

## 环境修正与复测（2026-10-10 晚）

| 修正 | 原因 |
|---|---|
| 工具报错文字不再含尖括号（如“经度须在 -180 到 180 之间，且 lon_min 小于 lon_max（西经为负）”）；动作解析错误改为说明规则的提示（plan 只能在开头、一句、≤160 字、不含尖括号；JSON 解析失败时指出位置） | 零样本中 884 轮协议违规由模型照抄报错里的“lon_min < lon_max”引起 |
| 剖面数上限从“每次查询”改为“每次计算/检查实际读取的剖面”（5 万条）；查询只读索引，上限 50 万条 | 跨多年的“两个月份对比”请求，查询跨度内可能有 9 万条剖面，但真正要计算的两个月各只有几百条；原设计下这种合理请求无法完成 |
| 抽样候选块只用有效坐标（训练年份中有纬度 −999、160 等填充值，会构成无效的“块”） | 训练请求中出现无效区域；开发与测试分区没有这种情况，开发集重新生成后与冻结版本一致 |

上述修正后测试与 oracle 检查都通过（48/48，180 个句柄与独立参考一致）。重新生成开发请求时，除一致性参考中新增的 `profiles_rejected_qc` 信息字段外，抽样、文字与全部参考数值与冻结的 `oceanlab_dev_v1` 一致；冻结文件保持不变。

报错文字修正后的 greedy 复测（`zeroshot-instruct-envfix-20261010-1946`，自带模板；该次运行早于后两项修正，后两项不影响这 48 条请求的正确流程）：

| greedy，48 条 | 修正前 | 修正后 |
|---|---:|---:|
| 科学成功 | 0 | 1（2.1%） |
| 出现协议违规的 episode | 54% | 33% |
| 无法解析的动作（轮） | 217 | 18 |
| 每条 episode 的工具错误 | 8.3 | 4.6 |
| 失败：预算耗尽 / 参数 / 交付格式 | 24 / 9 / 7 | 24 / 11 / 7 |

协议违规大幅减少，剩下的主要是参数映射和循环，属于 C0 示范要解决的问题。

## C0 示范数据

**训练请求** `data/processed/oceanlab/oceanlab_train_v1.jsonl`（sha256 `893a82ec…`）：
- 生成方式：与开发请求相同的预声明抽样（`scripts/oceanlab_make_requests.py --split train`）。
- 范围：训练分区内的 10° 块，扣除预留海域及其缓冲；月份为 2000-01～2016-11。
- 数量与配额：1,000 条，各任务族配额是开发集的 20.8 倍；混合层 375、势温一致性 210、盐度一致性 165、综合报告 250。
- 去重：完全相同的请求（任务族、区域、时段都一样）会重新抽。
- 核验：工具侧与参考侧在全部 1,000 条上一致。
- 状态分布：完整 534、部分 169、支持不足 297。支持不足比开发集多，因为 2000 年代初 Argo 稀疏。
- 规模：单条请求 0～28,398 条剖面。

**示范** `data/processed/oceanlab/c0/oceanlab_c0_demos_v1.jsonl`（sha256 `3daca88b…`）：
- 生成方式：每条训练请求的 oracle 轨迹，用 Instruct 自带模板通过 SDK 重放，保存的消息与推理时模型看到的完全一致。
- 核验：评分为 S=1，且没有环境错误或协议违规。1,000 条全部通过。
- **plan 的内容**：每个 plan 用一句话写明请求到参数的对应关系，例如“西经140°—西经130°→经度-140～-130”“上层200米即5.078～200 m”“一组：2009年11月至2010年1月”。交付前的 plan 写明支持状态是怎么判断的，例如“一致性有配对层 23/26→partial”。这些都只来自结构化规格和工具的公开输出，针对的正是零样本中最多的参数错误。
- **划分**：按固定随机顺序排列。最后 50 条留作验证损失；嵌套训练子集为前 250、500、950 条，在开发集上画学习曲线，决定 C0 需要多少示范。
- **覆盖**（950 条训练示范）：

| 维度 | 分布 |
|---|---|
| 任务族 | 混合层 358、势温一致性 199、盐度一致性 159、综合报告 234 |
| 状态 | 完整 506、部分 163、支持不足 281 |
| 时段写法 | 单月 244、季段 353、季段内逐月 120、两个月份 233 |
| 半球 | 东北 220、西北 282、东南 242、西南 206 |
| 深度起点 | 明确含 0.49 m 的 139 条 |

- **长度**：最后一轮提示平均 3,319、最长 4,255 个 token；每条示范的助手输出约 418 个 token。

## C0 SFT 学习曲线（进行中，`c0-sft-20261010-2037`）

训练脚本 `trainer/train_oceanlab_sft.py`：
- **样本**：每个助手轮是一个训练样本，输入为该轮推理时的完整提示，只对助手文本和结束 token 计算损失，logits 只在这些位置计算。
- **超参**：LoRA r16/α32，学习率 2e-4，3 个 epoch，有效 batch 16。
- **验证**：留出的 50 条示范算验证损失。

n250 的结果（训练 21 分钟，153 次更新）：
- **训练过程**：验证损失在第 50 步就从 1.36 降到 0.001。oracle 示范的文字非常规整，模型几乎完全记住。
- **开发集 48 条**：

| | greedy | 8 条采样 |
|---|---:|---:|
| 科学成功 | **48/48（100%）** | 97.4% |
| pass@8 | | 100% |
| 8 条结果有成有败的请求 | | 5/48 |
| 协议违规 | 0 | 0.5% |

- **失败与用量**：失败只有 8 次状态判断错、2 次句柄写错。每条 episode 2～3 次调用，累计输入约 8K token，约 18 秒。
- **结论**：**250 条示范就让开发集饱和。** 示范和开发请求来自同一套请求模板和措辞，开发集实际检验的是新区域、新时段下的同一种请求格式。按设计第 1、9 节，这种情况要如实报告饱和，不启动整组 RL。n500、n950 仍按计划在跑，用来确认学习曲线。

## 结论

1. 零样本 Instruct 会用这些工具，也大致理解流程：查询 → 计算 → 读结果 → 交付。但 S 为 0，pass@8 也为 0，而且没有科学奖励信号。因此 C0 冷启动 SFT 是必要的，这与设计一致。
2. 需要通过 C0 示范学会的内容按影响排序：
   - 把请求文字转成参数：分组、经纬度符号、深度起点；
   - 交付格式：句柄而不是数值，算完就交付；
   - 遵守协议，并能根据报错修正而不是重复。
3. 修改环境：报错文字不用尖括号，解析错误要说明 plan 的限制。改完后用 greedy 复测零样本，作为最终环境下的记录。
